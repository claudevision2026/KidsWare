# Spec: Multi-language UI (i18n)

## Scope
Only the app's own UI chrome is translated — nav, buttons, labels, form fields, and messages.
Admin/vendor-entered content (product names, descriptions, vendor/model names) is **not**
translated: it's free text typed by the admin in whatever language they used, and stays exactly as
entered regardless of the viewer's selected UI language. Admin-only pages (`pages/admin/*`,
`AdminLayout.jsx`) are also **not** translated — only the customer-facing storefront is (`Navbar`,
`Login`, `Register`, `Home`, `ProductDetails`, `HowToBuy`, `BuyNow`, `MyOrders`, `UserLayout`,
`Profile`, `ProductCard`, `WhatsAppButton`).

## Implementation
- `i18next` + `react-i18next` (`frontend/package.json`). Translations are bundled JSON, not fetched
  over HTTP — `frontend/src/i18n/index.js` inits `i18next` synchronously with all four languages'
  resources imported directly, so there's no loading flash on first paint.
- Locale files: `frontend/src/i18n/locales/{en,te,ta,hi}.json` — English, Telugu, Tamil, Hindi.
  Same nested key structure across all four files (namespaced by page/component, e.g.
  `login.title`, `profile.addresses.title`). `en.json` is the canonical structure; when adding a
  key, add it to all four files. The Telugu/Tamil/Hindi strings are a first-pass, AI-generated
  translation — worth a native-speaker review before this is taken as final/polished copy for
  production.
- Default language is English; persisted to `localStorage` under `ktw_language` and restored on
  load (`i18next.on('languageChanged', ...)` writes it, `lng: localStorage.getItem(...) || 'en'`
  reads it at init). No browser-locale auto-detection — an unset/first-time visitor always gets
  English, per explicit product decision.
- `frontend/src/components/LanguageSwitcher.jsx` — a small `<select>` calling
  `i18n.changeLanguage(code)`, mounted in `Navbar.jsx` so it's visible on every page.
- Components use `const { t } = useTranslation()` and `t('namespace.key', { interpolationVar })`.
  The brand name ("Kids Trendy Ware") and admin pages are deliberately left as plain strings, not
  translation keys.
- `formatAgeGroup` (`frontend/src/utils/format.js`) takes an optional `yearsLabel` param so the
  "X Years" age-group suffix can be localized on the two customer-facing call sites
  (`ProductDetails.jsx`, `BuyNow.jsx` pass `t('common.years')`); admin pages call it with no second
  arg and get the English default, matching the "admin pages stay English" scope decision above.

## Adding a new translated string
1. Add the key to `en.json` first, then mirror it into `te.json`/`ta.json`/`hi.json` (same nesting).
2. Reference it via `t('...')` in the component — don't hardcode the English string even
   temporarily, since the mixed-language JSX is easy to miss in a later pass.
3. If it needs to go on an admin-only page, it's out of scope per the decision above — leave that
   page's strings in plain English.

## Product description: live machine translation
Unlike the rest of the app, the product **Description** (admin-authored rich text) *is* translated
— on request, not stored — since asking admins to retype every description in four languages was
judged not worth it. This is a deliberate scope carve-out on top of the "UI text only" decision
above; nothing else about product/vendor data is translated.
- `backend/app/services/translation_service.py::translate_html` walks the description's HTML with
  BeautifulSoup and translates each text node individually (concurrently, via
  `asyncio.gather`) through the free [MyMemory](https://mymemory.translated.net/) API — this
  preserves the original `<p>`/`<span style=...>` formatting and emoji instead of collapsing to
  plain text. Optional `MYMEMORY_EMAIL` env var raises MyMemory's free daily quota; no API key is
  required otherwise.
  Results are cached in-process, keyed by a hash of `(target language, source HTML)` — editing a
  description naturally invalidates its cache entry (new hash) with no explicit invalidation code.
  The cache is memory-only and clears on backend restart; that's an accepted limitation, not a bug.
- `GET /api/products/{id}/description?lang={te|ta|hi}` (public, `backend/app/routers/products.py`)
  returns `{ description, translated }`; `translated: false` on any failure (unsupported lang,
  empty description, MyMemory error) — the caller then falls back to the original English HTML.
  A single node failing to translate doesn't fail the whole description — that fragment is just
  left in English.
- `frontend/src/pages/ProductDetails.jsx` fetches this whenever `i18n.language` isn't `'en'`,
  swapping in the translated HTML and showing an `machineTranslated` disclaimer line above it
  (machine translation isn't perfect — say so, don't pass it off as authored copy).
- Nothing else (product name, vendor/model name) goes through this — machine-translating short
  proper nouns/names tends to produce worse results than just leaving them as-is, and it wasn't
  asked for.
